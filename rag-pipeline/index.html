    Bird Q&A RAG Pipeline¶

    The app now includes a bird question-and-answer flow that uses the bird_species table as its knowledge base.

    The implementation now lives primarily in:

    • bird-agent/rag.py for retrieval, provider selection, and answer generation
    • bird-agent/main.py for the POST /bird-questions/ask and POST /bird-species-rag/rebuild route entrypoints
    • bird-agent/serializers.py for shared species-field extraction used when serializing matches

    At a high level:

    1. each bird_species row is turned into searchable text
    2. the question endpoint retrieves the best matching bird rows
    3. the system returns a short answer plus the top matching birds

    Recommended Hetzner Production Path¶

    The current recommended Hetzner production path is:

    • BIRD_RAG_RETRIEVAL_PROVIDER=local-semantic
    • BIRD_RAG_ANSWER_PROVIDER=ollama
    • OLLAMA_BASE_URL=http://127.0.0.1:11434/v1
    • OLLAMA_BIRD_RAG_CHAT_MODEL=gemma3:4b

    That means:

    • retrieval uses BM25 candidate retrieval plus MiniLM re-ranking
    • answer generation runs through a local Ollama service on the same box
    • the app still falls back to the local answer builder if Ollama is unavailable

    Local-Only Default¶

    The backend still supports a fully local no-LLM path:

    • BIRD_RAG_RETRIEVAL_PROVIDER=local
    • BIRD_RAG_ANSWER_PROVIDER=local

    That means:

    • retrieval uses cached BM25 matching over the generated bird documents
    • answer generation uses a local summary builder
    • OpenAI quota is not required for the default flow

    You can also enable a stronger local-only retrieval mode:

    BIRD_RAG_RETRIEVAL_PROVIDER=local-semantic
BIRD_RAG_ANSWER_PROVIDER=local

    That path keeps answer generation local, but switches retrieval to BM25 candidate retrieval with a cached sentence-transformers re-ranker and persisted local semantic embeddings.

    Optional Ollama Answer Path¶

    BIRD_RAG_RETRIEVAL_PROVIDER=local-semantic
BIRD_RAG_ANSWER_PROVIDER=ollama
OLLAMA_BASE_URL=http://127.0.0.1:11434/v1
OLLAMA_BIRD_RAG_CHAT_MODEL=gemma3:4b

    CPU-only server notes:

    • add swap before relying on Ollama on a 4GB VPS
    • cap Ollama context length:
    [Service]
Environment="OLLAMA_CONTEXT_LENGTH=2048"

    Optional OpenAI Path¶

    If you want to switch back to OpenAI later:

    BIRD_RAG_RETRIEVAL_PROVIDER=openai
BIRD_RAG_ANSWER_PROVIDER=openai
OPENAI_API_KEY=your_key_here

    Optional model overrides:

    OPENAI_BIRD_RAG_EMBEDDING_MODEL=text-embedding-3-small
OPENAI_BIRD_RAG_CHAT_MODEL=gpt-4o-mini

    Graceful Fallback¶

    Even when OpenAI is enabled, the backend now degrades gracefully:

    • if OpenAI retrieval fails, it falls back to local TF-IDF retrieval
    • if OpenAI answer generation fails, it falls back to the local answer builder
    • if local semantic retrieval fails, it falls back to local TF-IDF retrieval

    So the app can still return likely bird matches even when API quota or upstream AI availability is a problem.

    Local Cache Behavior¶

    The local retrieval modes now cache their working data in memory:

    • BM25 retrieval caches the tokenized species documents and a species-content hash
    • local semantic retrieval caches the loaded sentence-transformer model, generated species documents, a persisted local semantic embedding matrix, and a species-content hash

    The admin rebuild endpoint:

    • POST /bird-species-rag/rebuild

    now clears those in-memory caches before rebuilding, so the next request rehydrates them against the latest bird_species content. When the retrieval provider is local-semantic, the backend also refreshes the persisted local semantic embedding table.

    API Endpoints¶

    User-facing question endpoint:

    • POST /bird-questions/ask

    Admin rebuild endpoint:

    • POST /bird-species-rag/rebuild

    The question response includes:

    • question
    • answer
    • answer_source
    • retrieval_provider
    • answer_provider
    • warning
    • matches

    Refactor Notes¶

    The provider logic was intentionally extracted so switching retrieval or answer providers later is a configuration change rather than a rewrite. The rest of the backend should treat the bird-question flow as:

    1. route layer in main.py
    2. retrieval/answer orchestration in rag.py
    3. SQLite species source data from bird_species

    Matching Data Source¶

    Each bird_species row is currently converted into a document using:

    • common name
    • scientific name
    • family
    • order
    • habitat
    • diet
    • conservation status
    • and the extended descriptive fields used by the species detail flow, such as distribution, breeding notes, nest details, interesting facts, and FAQs

    This keeps the first-pass bird Q&A grounded in the structured species catalogue already stored in SQLite.
