    Admin Web¶

    The admin web is the browser-based administrative surface for Bird Platform.

    In coding terms, it is a separate React + Vite client in admin-web/ that talks directly to FastAPI admin endpoints in bird-agent/main.py. It is used for four main jobs:

    • species media management
    • user feedback reply handling
    • community moderation case review
    • promotions management

    Purpose¶

    The admin web exists so that operational and moderation tasks do not need to be performed from the mobile app UI.

    In coding terms, the older mobile admin review screens have been de-scoped and the browser admin is now the primary operational surface.

    It gives admin users a larger browser-based control surface for:

    • finding a species quickly
    • reviewing all stored gallery images for that species
    • choosing the default species image
    • reordering or hiding gallery rows
    • assigning quality metadata to species images and canonical audio
    • reviewing user support messages
    • replying to users through the backend-backed feedback thread
    • reviewing moderation cases created from community reports
    • creating, previewing, updating, activating, and deleting promotions

    Runtime Shape¶

    • frontend: admin-web/
    • stack: React, TypeScript, Vite
    • backend: FastAPI admin endpoints in bird-agent/main.py
    • auth: Firebase Auth sign-in on the client, Firebase ID token verification on the backend
    • data source of truth: backend database, not browser local state

    There are two practical runtime modes:

    1. local/dev mode
    2. deployed production mode

    In deployed environments, the admin UI and API can be served on separate hostnames while still sharing the same backend source of truth.

    Admin Views¶

    The current admin web has three top-level views:

    • species
    • reports
    • promos

    At a code level this is now modeled in admin-web/src/App.tsx as:

    type AdminView = "species" | "reports" | "promos";

    Inside reports, the admin first chooses one of four workflow lanes:

    • Comment / complaint
    • Report content
    • Report user
    • Block user

    This makes the reports workspace the single entry point for support, moderation, trust and safety, and self-serve safety actions.

    Authentication Flow¶

    The admin web signs the user in with Firebase Auth, then sends the Firebase ID token to the backend on each authenticated request.

    High-level flow:

    flowchart LR
    Admin["Admin user in browser"] --> UI["admin-web"]
    UI --> Firebase["Firebase Auth sign-in"]
    Firebase --> UI
    UI --> API["FastAPI admin endpoint + Bearer token"]
    API --> Auth["Backend token verification"]
    Auth --> DB["PostgreSQL-backed app database"]
    DB --> API
    API --> UI

    Important behavior:

    • the backend still decides whether the authenticated user is an admin
    • non-admin or guest users are rejected from admin endpoints

    API Surface¶

    The admin web currently uses these backend endpoints directly:

    Species media¶

    • GET /admin/species
    • GET /admin/species/{species_id}/images
    • PATCH /admin/species/{species_id}/default-image
    • PATCH /admin/species/{species_id}/image-order
    • PATCH /admin/species/{species_id}/sound-quality

    Feedback¶

    • GET /admin/feedback
    • PATCH /admin/feedback/{feedback_id}/reply

    The feedback lane now reads threaded support tickets backed by:

    • user_feedback
    • user_feedback_messages

    Moderation¶

    • GET /admin/community-reports
    • PATCH /admin/community-reports/{report_id}

    Promotions¶

    • GET /admin/promotions
    • POST /admin/promotions
    • PATCH /admin/promotions/{promotion_id}
    • DELETE /admin/promotions/{promotion_id}

    The moderation payload now also carries:

    • report_lane
    • severity_label
    • severity_score
    • outcome
    • content_action_type
    • trust and safety action history
    • reported-user safety-signal summaries

    Promo Workspace¶

    The Promos workspace is a browser-based operational surface for promotion management.

    It allows admins to:

    • create a promotion row without writing SQL
    • edit all key fields used by the mobile app promotion flow
    • preview the card visually before saving
    • delete obsolete promotions cleanly

    This is backed by the same PostgreSQL promotions table consumed by the app.

    Typical editable fields include:

    • slug
    • title
    • body
    • image URL or bundled asset key
    • CTA label
    • CTA target
    • background color
    • active / inactive state
    • start and end timestamps
    • priority
    • display-after-login delay
    • repeat frequency

    This admin workflow is especially useful for:

    • launch messaging
    • timed feature campaigns
    • image-only advert cards
    • testing and operational verification without direct DB access

    Promo Create / Edit Flow¶

    At a high level, the promo workspace behaves like this:

    flowchart LR
    A["Admin user"] --> B["Promos workspace form"]
    B --> C["POST/PATCH admin promotion API"]
    C --> D["FastAPI promotion service"]
    D --> E["PostgreSQL promotions table"]
    E --> D
    D --> C
    C --> F["Updated promo returned to browser"]

    In public architecture terms:

    • the browser form owns draft state only
    • the backend remains the source of truth
    • the promotions table stores the promo definition itself
    • per-user delivery and cooldown behavior is tracked separately from the promo definition

    Promo Data Model¶

    The promotions feature uses a split model:

    1. Promotion definition Stored as a backend record describing the card itself.
    2. Per-user interaction state Stored separately so the app can track whether a given user has already seen, dismissed, or clicked a promo.
    flowchart TD
    A["Admin creates or edits promo"] --> B["Promotion definition"]
    B --> C["App can render this promo"]
    D["User sees / dismisses / clicks promo"] --> E["Per-user interaction state"]
    E --> F["Cooldown + audit behavior"]

    This separation is useful because it lets the product team change campaign content without mixing that concern with user-level delivery telemetry.

    Ticketing And Safety Model¶

    The admin and safety system works best when it is treated as four distinct flows rather than one generic ticket queue.

    This documentation describes the intended operating model:

    • comment / complaint
    • report content
    • report user
    • block user

    These flows have different risk levels, different automation, and different human-review requirements.

    Reports Workspace Model¶

    When the admin enters Reports, they should not land directly in a mixed queue of unrelated case types.

    Instead, the workspace starts with four clear choices:

    flowchart TD
    A["Reports workspace"] --> B["Comment / complaint"]
    A --> C["Report content"]
    A --> D["Report user"]
    A --> E["Block user"]

    B --> B1["Support ticket path"]
    C --> C1["Content moderation path"]
    D --> D1["Trust & safety path"]
    E --> E1["Immediate self-serve block path"]

    This is the interface model now reflected in the admin web.

    Workspace Screenshot¶

    The current browser admin now presents the reports area as a single wide Reports Workspace with:

    • a collapsible sidebar
    • unified lane chips
    • pipeline/list/analytics views
    • top-level SLA metrics
    • stage-grouped ticket columns

    Lane purpose¶

    • Comment / complaint This lane surfaces support-style user/admin conversation threads and agent replies.
    • Report content This lane handles post and comment moderation cases, including severity classification, binary outcome, and content-level actions.
    • Report user This lane handles account-level trust and safety cases, including enforcement actions and behavioural-signal review.
    • Block user This lane documents the immediate self-serve block behavior and its role as a safety signal, rather than treating it as a human review queue.

    Comment / Complaint Flow¶

    Comment / complaint is the support lane rather than the moderation lane.

    Key characteristics:

    • creates a support ticket
    • can pass through sentiment analysis or other prioritisation signals
    • requires a human agent response
    • remains open as a two-way conversation until the user is satisfied

    This flow is best aligned with the feedback-style thread model, where the same underlying case can hold:

    • the original user message
    • the admin or support reply
    • follow-up conversation and resolution state

    Report Content Flow¶

    Report content is the standard content moderation lane.

    Key characteristics:

    • targets a specific piece of content
    • is auto-classified for severity before human review
    • still ends with a human moderation decision
    • has a binary case outcome:
    • action
    • no action
    • notifies both the reporter and the content author

    This flow is narrower than trust-and-safety account review because the primary focus is the reported content item rather than the account's complete behavioural history.

    In the current backend model, this lane now persists:

    • report_lane = report_content
    • auto-classified severity_label and severity_score
    • outcome = action_taken | no_action
    • optional content_action_type
    • notification timestamps for the reporter and the content owner

    Report Management UI¶

    The reports workspace is evolving from a simple stacked review form into a report-management dashboard.

    In coding terms, the moderation UI now maps the workflow model into a pipeline-oriented screen with:

    • stage columns that mirror the workflow:
    • New
    • Triaging
    • In review
    • Decision
    • Action
    • Closed
    • ticket cards that carry lane/type badges using the same visual language as the safety model:
    • comment
    • report content
    • report user
    • block
    • SLA state on each card so moderators can scan queue health quickly:
    • healthy
    • at risk
    • breached
    • a summary metrics bar at the top for:
    • open tickets
    • SLA at risk
    • SLA breached
    • closed today
    • multiple workspace views:
    • pipeline view
    • list view
    • analytics
    • a detail panel for the selected ticket showing:
    • ticket summary
    • reporter and subject user
    • priority and severity
    • lifecycle timeline
    • the currently active workflow action area

    Lifecycle timeline behavior¶

    The detail panel mirrors the workflow diagram directly.

    • completed stages render as completed
    • the current stage renders as active
    • future stages render as pending

    This allows the ticket detail panel to act as a live operational version of the workflow diagram rather than a separate UI concept.

    Stage-aware editing¶

    Only the current actionable stage should be visible while the case is in progress.

    In coding terms, this means:

    • future workflow sections should not be shown early
    • the card should expose only the current action area
    • once the case reaches notification_sent, it should be treated as resolved
    • resolved cards should collapse by default
    • resolved cards should show the notification state and offer a Re-open case action

    This keeps the UI closer to a real moderation queue and avoids overwhelming moderators with fields that are not relevant yet.

    Report User Flow¶

    Report user is the trust-and-safety lane.

    Key characteristics:

    • more serious than reporting one content item
    • evaluates the user account more broadly
    • looks at account history and behavioural signals
    • supports escalating outcomes:
    • warn
    • temporary suspend
    • permanent ban

    In the current backend model, this lane now persists:

    • report_lane = report_user
    • trust and safety actions in trust_safety_actions
    • derived behavioural signals in user_safety_signals
    • signal summaries returned to the admin UI for account-level review

    This flow is better modeled as an account-level review rather than a single-post moderation ticket.

    Block User Flow¶

    Block user is intentionally different from the ticket-based flows.

    Key characteristics:

    • immediate self-serve action
    • no moderation queue
    • no human review step
    • no support ticket requirement
    • immediate effect for the blocking user

    Even though it is silent from the user's perspective, the block event should still be logged as a safety signal so it can contribute to:

    • bad-actor detection
    • abuse heuristics
    • trust-and-safety model feedback

    Enforcement And Resolution¶

    Across these flows, enforcement and resolution are not the same thing.

    Enforcement¶

    Enforcement actions include:

    • content action
    • warning
    • temporary suspension
    • permanent ban

    These are intervention steps.

    Resolution¶

    Resolution states include:

    • support conversation closed
    • moderation case resolved
    • trust-and-safety case resolved
    • silent user-level block completed

    These indicate that the flow has reached an operational end state, whether or not enforcement occurred.

    Current Product Shape Versus Target Shape¶

    The current product already separates some of these concerns, but the target model is broader and clearer:

    • feedback flows already exist and map naturally to comment / complaint
    • community moderation reports already exist and map naturally to report content
    • user-report handling exists, but the trust-and-safety lane should be treated as more account-centric than standard content moderation
    • user blocking already exists as an immediate self-serve action and should remain outside the human review queue

    The main design improvement is to treat these as four distinct operating lanes rather than one shared ticket concept.

    How Species Media Management Works¶

    This is the core admin-web workflow today.

    Read flow¶

    1. Admin signs in.
    2. Admin searches species with GET /admin/species.
    3. Admin selects a species.
    4. Admin web fetches the species payload and gallery rows with GET /admin/species/{species_id}/images.
    5. Backend returns:
    6. species identity
    7. default image
    8. ordered gallery rows
    9. canonical song/call audio URLs
    10. sound-quality metadata

    Edit flow¶

    Inside the species manager, the admin can:

    • choose a new default image
    • move visible images up or down
    • hide an image from the gallery
    • restore a hidden image
    • adjust image_quality
    • adjust canonical song_audio_quality and call_audio_quality

    Save behavior¶

    The admin web writes two separate concepts:

    • default image selection
    • gallery/image-quality ordering

    Default image write:

    • PATCH /admin/species/{species_id}/default-image
    • backend updates bird_species.default_image_url

    Gallery and image-quality write:

    • PATCH /admin/species/{species_id}/image-order
    • backend updates bird_detail.display_order
    • backend updates bird_detail.image_quality

    Sound quality write:

    • PATCH /admin/species/{species_id}/sound-quality
    • backend updates bird_species.song_audio_quality
    • backend updates bird_species.call_audio_quality

    Hidden image rule¶

    The admin web does not delete gallery rows when removing them from the visible gallery.

    Instead:

    • visible rows use display_order = 0..N
    • hidden rows use display_order = 999

    So Remove is really a hide operation, and Restore moves the row back into the visible ordered set.

    Species Media Workflow Diagram¶

    flowchart TD
    Admin["Admin"] --> Search["Search species"]
    Search --> SpeciesAPI["GET /admin/species"]
    SpeciesAPI --> Select["Select species"]
    Select --> ImagesAPI["GET /admin/species/{id}/images"]
    ImagesAPI --> Edit["Reorder / hide / set default / set quality"]
    Edit --> DefaultAPI["PATCH default-image"]
    Edit --> OrderAPI["PATCH image-order"]
    Edit --> SoundAPI["PATCH sound-quality"]
    DefaultAPI --> BirdSpecies["bird_species.default_image_url"]
    OrderAPI --> BirdDetail["bird_detail.display_order + image_quality"]
    SoundAPI --> BirdSpeciesAudio["bird_species song/call audio quality"]

    Comment / Complaint Workflow¶

    The Comment / complaint lane is the admin side of the user support-message system.

    User flow¶

    1. A signed-in user sends a support message from the app.
    2. Backend stores the ticket header in user_feedback.
    3. Backend stores the thread message in user_feedback_messages.
    4. That ticket becomes visible to admins through GET /admin/feedback.

    Admin flow¶

    1. Admin opens Reports.
    2. Admin chooses Comment / complaint.
    3. Admin fetches feedback items through GET /admin/feedback.
    4. Admin writes a reply.
    5. Admin web submits PATCH /admin/feedback/{feedback_id}/reply.
    6. Backend updates:
    7. user_feedback_messages
    8. user_feedback.admin_response
    9. user_feedback.admin_user_id
    10. user_feedback.status = 'waiting_on_user'
    11. user_feedback.responded_at
    12. user_feedback.last_message_at
    13. The user later fetches the same ticket from the app and sees the response.

    User-close and stale-close behavior¶

    The admin support lane should assume that support tickets are never hard-deleted from the database during normal user handling.

    Instead:

    • a user may close their own ticket from the app, which sets user_feedback.status = 'closed_by_user'
    • the backend stale sweep may close waiting_on_user tickets after 7 days, which sets status = 'resolved'
    • both outcomes should remain visible as historical closed tickets rather than disappearing from audit history

    Key rule¶

    The conversation is not stored as the main record on the phone and is not stored in Firebase as an application thread.

    The source of truth is the backend ticket model in user_feedback plus user_feedback_messages.

    Moderation Workflow¶

    The Report content and Report user lanes are the admin side of community moderation and trust and safety review.

    User-side report creation¶

    Users can report:

    • predictions
    • comments
    • users

    Those actions create rows in community_reports.

    Admin-side review¶

    The admin web loads moderation cases through GET /admin/community-reports.

    Each report can include joined context from:

    • the reporter user
    • the reported user
    • the related prediction
    • the related comment
    • the admin reviewer

    The current workflow is intentionally forward-only. In the current product shape, the admin moves a report through stages such as:

    • ticket_created
    • priority_triage
    • moderator_review
    • policy_decision
    • enforcement_action
    • notification_sent

    The admin web writes updates through PATCH /admin/community-reports/{report_id}.

    This updates moderation fields such as:

    • report_lane
    • workflow_stage
    • priority
    • severity_label
    • severity_score
    • outcome
    • content_action_type
    • admin_note
    • admin_reply
    • decision_note
    • enforcement_note
    • notification_message
    • reporter_notified_at
    • reported_user_notified_at
    • admin_user_id
    • reviewed_at

    For Report user cases, the backend can also write:

    • trust_safety_actions
    • user_safety_signals

    User/Admin Use-Case Flows¶

    Use case: admin manages a species gallery¶

    1. Admin logs into the admin web.
    2. Admin searches for a species.
    3. Admin opens the species gallery manager.
    4. Admin reviews ordered image rows.
    5. Admin sets one row as default.
    6. Admin hides weak images or reorders visible images.
    7. Admin adjusts image and audio quality metadata.
    8. Backend persists the change.
    9. Mobile app and other backend-powered screens read the updated ordering/default image on the next fetch.

    Use case: user sends support feedback and admin replies¶

    1. User submits a support message from the app.
    2. Backend stores the row in user_feedback.
    3. Admin opens the feedback view in admin web.
    4. Admin reads the message and replies.
    5. Backend stores the reply and the responding admin id.
    6. User later reopens support messages and sees the admin response.

    Use case: user reports community content and admin reviews it¶

    1. User reports a post, comment, or user from the community experience.
    2. Backend stores a community_reports row.
    3. Admin opens Reports.
    4. Admin chooses either Report content or Report user.
    5. Admin reviews the joined context.
    6. Admin advances the workflow stage and records severity, outcome, trust-and-safety actions, moderation notes, and user-facing updates.
    7. The report remains part of the backend moderation record for later audit or follow-up.

    Database Structure¶

    The admin web is only a client surface. The actual state lives in backend tables.

    Core admin-managed tables¶

    bird_species¶

    Relevant admin-facing fields:

    • default_image_url
    • song_audio_url
    • call_audio_url
    • song_audio_quality
    • call_audio_quality

    Admin meaning:

    • stores the chosen default species image
    • stores the canonical song/call assets and their quality grades

    bird_detail¶

    This is the source of truth for ordered species gallery images.

    Relevant admin-facing fields:

    • bird_species_id
    • image_url
    • display_order
    • image_quality
    • source_name
    • source_record_id
    • managed_by
    • managed_rank
    • is_managed

    Admin meaning:

    • each row is one species image
    • order is driven by display_order
    • hidden rows use display_order = 999
    • image_quality is editable from the admin web

    user_feedback¶

    Relevant admin-facing fields:

    • user_id
    • subject
    • message
    • status
    • admin_response
    • admin_user_id
    • responded_at
    • last_message_at
    • resolved_at

    Admin meaning:

    • stores support ticket headers
    • the actual thread messages live in user_feedback_messages

    user_feedback_messages¶

    Relevant admin-facing fields:

    • feedback_id
    • author_user_id
    • author_role
    • message
    • created_at

    Admin meaning:

    • stores the support conversation thread
    • allows the admin web to show a proper two-way ticket history

    community_reports¶

    Relevant admin-facing fields:

    • reporter_user_id
    • prediction_id
    • comment_id
    • reported_user_id
    • report_lane
    • reason
    • details
    • status
    • workflow_stage
    • priority

    Read/Write Responsibilities¶

    The admin web does not own business rules. The backend does.

    The client is responsible for:

    • login initiation through Firebase
    • rendering admin views
    • sending structured update payloads

    The backend is responsible for:

    • verifying Firebase identity
    • enforcing admin-only access
    • validating ordering and payload shape
    • resolving media paths into signed URLs
    • persisting updates into database tables

    Examples of backend validation:

    • visible gallery orders must be contiguous starting at 0
    • hidden rows must use display_order = 999
    • image-order payload must include every image row exactly once
    • default image must belong to the selected species

    How Changes Affect the App¶

    Admin-web changes are immediately important to the rest of the platform because the mobile app and API read the same backend data.

    Examples:

    • changing bird_species.default_image_url changes species thumbnails and default detail images
    • changing bird_detail.display_order changes gallery order in detail screens
    • hiding rows removes them from visible gallery payloads while keeping them in the database
    • replying to feedback changes what the user sees in support-message history
    • updating moderation records changes admin review state for community cases
