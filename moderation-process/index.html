    Moderation Process

    Community Moderation And Support Workflows¶

    Spark Birds has two separate user-message systems:

    1. Community comments are public messages on community prediction posts.
    2. Settings/support feedback is a private support thread between a user and administrators.

    These systems must stay separate in the code, database, admin screens, and documentation.

    1. Community Comments And Public Post Interaction¶

    Community comments belong to the public community feed. They are visible to users who can view the community prediction post.

    flowchart TD
    A["User views community prediction post"] --> B{"User action"}

    B -->|Adds comment| C["Create community prediction comment"]
    C --> D["community_prediction_comments row created"]
    D --> E["Comment visible on community post"]

    B -->|Rates or reacts| F["Rating / reaction saved"]
    F --> G["Community post metrics updated"]

    B -->|Reports post| H["Create community report"]
    H --> I["community_reports row created<br/>target: prediction"]

    B -->|Reports comment| J["Create community report"]
    J --> K["community_reports row created<br/>target: comment"]

    B -->|Reports user| L["Create community report"]
    L --> M["community_reports row created<br/>target: user"]

    B -->|Blocks user| N["Create user block"]
    N --> O["user_blocks row created"]
    O --> P["Blocked user filtered from feed, comments, ratings, reactions, and future interactions"]

    I --> Q["Admin moderation workflow"]
    K --> Q
    M --> Q

    2. Report Lane Classification¶

    Community reports are grouped into lanes so the admin workspace can understand the type of case.

    flowchart TD
    A["community_reports row"] --> B{"Report target"}

    B -->|prediction_id exists| C["Content lane"]
    B -->|comment_id exists| D["Content lane"]
    B -->|reported_user_id exists| E["User lane"]

    C --> F["report_lane = report_content"]
    D --> F
    E --> G["report_lane = report_user"]

    F --> H["Content moderation review"]
    G --> I["User behaviour / risk review"]

    Content-lane reports cover reported posts and reported comments. User-lane reports cover reports about another user.

    3. Admin Moderation Workflow¶

    A community report moves through the admin moderation workflow. The internal workflow stage is more detailed than the user-facing status.

    flowchart TD
    A["community_reports row created"] --> B["ticket_created"]
    B --> C["priority_triage"]
    C --> D["moderator_review"]
    D --> E["policy_decision"]
    E --> F{"Account enforcement needed?"}

    F -->|No| G["notification_sent"]
    F -->|Yes| H["enforcement_action"]

    H --> I["notification_sent"]
    G --> J["Reporter sees update in Settings"]
    I --> J

    Allowed stage transitions¶

    The backend enforces strict workflow transitions so reports cannot skip required review steps unless a valid follow-up path applies.

    Current stage Allowed next stage(s)
    ticket_created priority_triage
    priority_triage moderator_review
    moderator_review policy_decision
    policy_decision enforcement_action, notification_sent
    enforcement_action notification_sent
    notification_sent none through normal progression
    reporter_follow_up moderator_review, policy_decision, notification_sent

    Important backend rules:

    • priority_triage requires a priority value.
    • moderator_review requires an admin reply.
    • policy_decision requires a decision note.
    • notification_sent requires a notification message.
    • Content-lane reports can use content_action_type but not trust and safety actions.
    • User-lane reports can use trust_safety_action_type but not content actions.

    User-facing status mapping¶

    Workflow stage User-facing status
    ticket_created open
    priority_triage open
    moderator_review reviewing
    policy_decision reviewing
    enforcement_action reviewing
    notification_sent resolved

    4. Reporter Response Loop¶

    After an admin response or final notification, the reporter may be allowed to respond.

    flowchart TD
    A["Admin sends moderation update"] --> B["Reporter sees case update in Settings"]
    B --> C{"Can user respond?"}

    C -->|No| D["Case remains read-only"]
    C -->|Yes| E["User writes response"]
    E --> F["user_response saved on community_reports"]
    F --> G["user_responded_at timestamp saved"]
    G --> H["workflow_stage = reporter_follow_up"]
    H --> I["status = reviewing"]
    I --> J["Case returns to admin queue"]
    J --> K{"Admin next step"}
    K --> L["Admin moves case to moderator_review"]
    K --> M["Admin moves case to policy_decision"]
    K --> N["Admin closure from admin site"]
    N --> O["workflow_stage = notification_sent"]
    O --> P["status = resolved"]

    This prevents user responses from disappearing. A reporter response should bring the case back to admin attention.

    Admin closure after reporter follow-up¶

    If the reporter replies and no further investigation is needed, the admin does not have to replay the whole workflow from the beginning.

    The admin may:

    1. move the case back to moderator_review
    2. move the case to policy_decision
    3. close directly from reporter_follow_up by setting workflow_stage = notification_sent

    This direct admin closure path still requires a final notification_message, because the user needs a visible closing message in Settings and Closed Cases.

    5. Content Actions¶

    Content action is separate from user/account enforcement. A policy decision can affect the reported content, the reported user, both, or neither. The stored content_action_type decision can be content_removed, content_hidden, warning_only, or no_content_action.

    flowchart TD
    A["Policy decision"] --> B{"Content action needed?"}

    B -->|Remove| C["content_removed"]
    B -->|Hide| D["content_hidden"]
    B -->|Warning only| E["warning_only"]
    B -->|No content action| F["no_content_action"]

    C --> G["content_action_type saved"]
    D --> G
    E --> G
    F --> G

    G --> H["Decision note / admin reply saved"]

    Expected content actions:

    Action Meaning
    content_removed Content should no longer be available.
    content_hidden Content is hidden from normal users but may remain available for review/audit.
    warning_only Content remains visible, but the user receives a warning or guidance.
    no_content_action No content-level action is required.

    6. Trust And Safety Actions¶

    Trust and safety actions are account-level decisions. They are separate from content actions.

    flowchart TD
    A["Policy decision"] --> B{"User/account action needed?"}

    B -->|Warn user| C["warn"]
    B -->|Temporary suspension| D["temporary_suspend"]
    B -->|Permanent ban| E["permanent_ban"]
    B -->|No user action| F["no_trust_action"]

    C --> G["trust_safety_action_type saved on report<br/>trust_safety_actions row created"]
    D --> G
    E --> G
    F --> H["trust_safety_action_type = no_trust_action<br/>No trust_safety_actions row created"]

    G --> I["Admin risk view updated"]
    I --> J["Notification prepared"]

    Expected trust and safety actions:

    Action Meaning
    warn User receives a warning but can continue using the app.
    temporary_suspend User is suspended for a limited period.
    permanent_ban User account is permanently banned.
    no_trust_action No account-level action is required.

    7. Safety Signals¶

    Safety signals are not the same as moderation cases. They are supporting risk indicators used by the admin to understand repeated behaviour.

    flowchart TD
    A["User reports another user"] --> B["Safety signal logged<br/>source: user_report"]
    C["User blocks another user"] --> D["Safety signal logged<br/>source: user_block"]

    B --> E["Reported user risk view"]
    D --> E

    E --> F["Admin reviews risk history"]
    F --> G["Policy decision"]

    Safety signals should help answer questions such as:

    • Has this user been reported before?
    • Has this user been blocked by several people?
    • Are reports isolated or repeated?
    • Is stronger trust and safety action needed?

    8. Settings / Support Feedback Thread¶

    Settings/support feedback is private. It does not create a community report unless the admin explicitly decides to escalate it.

    flowchart TD
    A["User opens Settings / Support"] --> B["User submits feedback"]
    B --> C["user_feedback row created"]
    C --> D["Initial user message stored in user_feedback_messages"]
    D --> E["Status: waiting_on_admin"]

    E --> F["Admin sees ticket in feedback workspace"]
    F --> G["Admin replies"]
    G --> H["Admin message stored in user_feedback_messages"]
    H --> I["Status: waiting_on_user"]

    I --> J["User sees admin reply in Settings"]
    J --> K{"User next action"}

    K -->|Reply| L["POST /feedback/:id/messages"]
    L --> M["User message stored in user_feedback_messages"]
    M --> N["Status: waiting_on_admin"]
    N --> F

    K -->|Close| O["PATCH /feedback/:id/resolve"]
    O --> P1["Status: closed_by_user"]
    P1 --> P["Closed Cases"]

    K -->|No action| Q["Ticket remains waiting_on_user"]
    Q --> R["Backend sweep closes stale waiting_on_user tickets after 7 days"]
    R --> S["Status: resolved"]
    S --> P

    Feedback status cycle¶

    Status Meaning
    waiting_on_admin User has sent a message and admin needs to reply.
    waiting_on_user Admin has replied and the user may respond or resolve the ticket.
    closed_by_user User explicitly closed their own ticket from the app.
    resolved Ticket is closed.

    Support ticket closure rules¶

    Support tickets can become resolved in three different ways:

    Closure path How it happens Expected stored effect
    Admin closes after reply Admin sends a reply with status = resolved ticket is resolved and a status-history event is written
    User closes own ticket User calls the resolve flow for the ticket they created ticket becomes closed_by_user and a status-history event is written
    Automatic stale sweep Backend sweep closes waiting_on_user tickets with no reply for 7 days ticket is resolved and an automatic-close history event is written

    Closed Cases behaviour¶

    The Settings experience should separate active items from closed items:

    • active moderation items remain in the open/in-progress view until notification_sent
    • active support tickets remain in the open/in-progress view until resolved or closed_by_user
    • resolved moderation items should appear in Closed Cases
    • resolved or user-closed support tickets should appear in Closed Cases
    • final admin messages and closure notes should remain readable on mobile

    9. Automated Test Coverage¶

    The workflow is now covered in both isolated backend tests and live API tests.

    Backend pytest coverage¶

    Backend workflow rules are covered in:

    • bird-agent/tests/test_moderation_service.py
    • bird-agent/tests/test_feedback_service.py

    Current automated checks include:

    • rejecting invalid moderation workflow jumps
    • rejecting lane/action mismatches
    • moving reporter replies back to reporter_follow_up
    • rejecting reporter replies before a decision stage
    • allowing admin closure after reporter follow-up
    • rejecting admin closure without a required notification message
    • allowing user-initiated support-ticket closure
    • rejecting support-ticket closure by a non-owner
    • closing stale waiting_on_user support tickets
    • dry-run reporting for the stale sweep without writing changes
    • ignoring fresh or invalid stale-sweep candidates

    Live API coverage¶

    Live workflow checks are covered in:

    • tests/live/test_moderation_live_api.py

    This test validates:

    • Firebase login for reporter, reported user, normal user, and admin accounts
    • admin access control for moderation endpoints
    • reporter access to their own moderation history
    • prediction creation and community sharing
    • comment creation and comment reporting
    • admin progression from ticket_created to notification_sent
    • reporter follow-up after a resolved moderation decision
    • admin re-closure after follow-up
    • final resolved state after admin closure

    Recommended commands¶

    Run backend workflow tests:

    ./bird-agent/.venv/bin/pytest bird-agent/tests/test_moderation_service.py
./bird-agent/.venv/bin/pytest bird-agent/tests/test_feedback_service.py

    Run live moderation tests:

    ./bird-agent/.venv/bin/pytest tests/live/test_moderation_live_api.py
RUN_LIVE_MODERATION_WRITE_TESTS=1 ./bird-agent/.venv/bin/pytest tests/live/test_moderation_live_api.py -s

    The write-enabled live run should only be used against the PostgreSQL-backed live environment with valid Firebase and API credentials in .env.live-tests.

    10. System Boundary Summary¶

    Area Public or private Main storage Admin workflow
    Community post Public community_predictions / shared predictions Only enters moderation if reported
    Community comment Public community_prediction_comments Only enters moderation if reported
    Reported post Private moderation case community_reports Admin moderation workflow
    Reported comment Private moderation case community_reports Admin moderation workflow
    Reported user Private moderation case community_reports Admin moderation workflow plus safety signal
    Blocked user Private user action user_blocks Safety signal / risk context
    Support feedback Private support ticket user_feedback Admin feedback workflow
    Feedback messages Private thread messages user_feedback_messages Admin feedback workflow
    Content action Admin decision content_action_type / moderation metadata Created after policy decision
    Trust and safety action Admin decision trust_safety_actions Created after policy decision
    Safety signal Admin risk context safety signal storage Feeds reported-user risk view

    11. Important Implementation Notes¶

    • A community comment is public.
    • A support feedback message is private.
    • A reported comment should become a community_reports case with a report_content lane.
    • A reported user should become a community_reports case with a report_user lane.
    • Reporting or blocking a user should create a safety signal.
    • Content actions and trust actions should be treated as separate decisions.
    • A user response to a moderation decision should update workflow_stage to reporter_follow_up and return the case to admin attention.
    • From reporter_follow_up, an admin may re-open review, move straight to policy decision, or send an administrative closure from the admin site when no further review is needed.
    • Feedback tickets should cycle between waiting_on_admin, waiting_on_user, and a closed state of either closed_by_user or resolved.
