    Backend Overview¶

    The backend lives in bird-agent/ and now follows a much cleaner FastAPI structure than the earlier single-file main.py design.

    The important architectural shift is:

    • bird-agent/main.py is now a thin ASGI entrypoint
    • bird-agent/app_factory.py is the application composition root
    • HTTP transport is split into routers by domain
    • business workflow is split into service modules
    • SQL access is split into repository modules
    • database bootstrap/schema/migration logic is split out of the web entrypoint

    That means the backend now more closely follows the industry-standard Python layering:

    • router -> service -> repository
    • app_factory -> startup/lifespan orchestration
    • core -> config/constants/paths
    • app_db -> connection/schema/migrations/bootstrap

    Layer Responsibilities¶

    The backend layers are intentionally strict.

    Router¶

    Router modules are HTTP-only.

    Their responsibilities are:

    • request params
    • auth dependency application
    • response shape
    • request model parsing through FastAPI/Pydantic
    • handing off work to the service layer

    Router modules should not own:

    • SQL
    • workflow state transitions
    • transaction orchestration
    • non-trivial domain rules

    Service¶

    Service modules own business behavior.

    Their responsibilities are:

    • business rules
    • validation flow
    • workflow transitions
    • transaction orchestration
    • deciding which repository calls happen and in what order
    • coordinating shared helpers such as serializers, moderation helpers, and media cleanup

    Service modules should not own:

    • raw SQL strings
    • route decorators
    • FastAPI dependency declarations

    Repository¶

    Repository modules are persistence-only.

    Their responsibilities are:

    • SQL only
    • fetch rows
    • update rows
    • insert rows
    • delete rows
    • aggregate queries
    • join queries

    Repository modules should not own:

    • FastAPI concerns
    • HTTPException
    • auth logic
    • moderation workflow rules
    • prediction/community business decisions

    This separation is now the core design rule for new backend work.

    Current Entry Points¶

    • bird-agent/main.py now only exposes app = create_app()
    • bird-agent/app_factory.py builds the FastAPI app, mounts static files, includes routers, and runs lifecycle startup through a FastAPI lifespan function

    Current Module Layout¶

    Core and Bootstrap¶

    • bird-agent/core/config.py environment loading and runtime flags
    • bird-agent/core/paths.py local filesystem paths and upload directories
    • bird-agent/app_db/connection.py SQLite/Postgres compatibility connection factory
    • bird-agent/app_db/schema.py base table creation
    • bird-agent/app_db/migrations.py schema evolution and data backfills
    • bird-agent/app_db/bootstrap.py startup database initialization orchestration
    • bird-agent/alembic-main-app.ini Alembic config for the primary app PostgreSQL database
    • bird-agent/alembic_main_app versioned migrations for the primary app PostgreSQL database

    Database Demarcation¶

    The repo now has two distinct Alembic migration trees and they do not own the same database.

    1. Main app database
    2. env var: DATABASE_URL
    3. production database name is typically bird_platform
    4. owns tables such as users, bird_species, predictions, community_reports, user_feedback, and trust_safety_actions

    5. Alembic config:

      • bird-agent/alembic-main-app.ini
      • bird-agent/alembic_main_app/

    6. Nearby alerts database

    7. env vars:
      • BIRD_ALERTS_DATABASE_URL
      • BIRD_ALERTS_DATABASE_URL_SYNC
    8. production database name is typically birdagent
    9. owns the nearby-alert scheduling/user tables only
    10. Alembic config:
      • bird-agent/alembic-nearby-bird-alerts.ini
      • bird-agent/alembic_nearby_bird_alerts/

    Operational rule:

    • schema changes in the main product tables should go through the main-app Alembic tree
    • schema changes in nearby-alerts tables should go through the nearby-alerts Alembic tree
    • runtime bootstrap helpers in app_db/schema.py and app_db/migrations.py remain useful reference code, but production PostgreSQL schema evolution should now be handled through Alembic

    • bird-agent/community/router.py community HTTP routes

    Feedback¶

    • bird-agent/feedback/repository.py feedback ticket/message SQL
    • bird-agent/feedback/service.py user/admin support ticket workflows
    • bird-agent/feedback/helpers.py threaded feedback serialization
    • bird-agent/feedback/router.py feedback HTTP routes

    Moderation¶

    • bird-agent/moderation/repository.py moderation update and trust-safety SQL helpers
    • bird-agent/moderation/service.py moderation workflow/state-transition logic
    • bird-agent/moderation/helpers.py severity classification, trust-safety actions, and signal logging
    • bird-agent/moderation/sla.py SLA, report stage, and feedback/report normalization logic
    • bird-agent/moderation/queries.py report retrieval and serialization queries
    • bird-agent/moderation/router.py moderation/admin HTTP routes

    Promotions¶

    • bird-agent/promotions/repository.py promotion SQL, admin CRUD persistence, and per-user promotion state updates
    • bird-agent/promotions/service.py promotion eligibility logic, timing resolution, serialization, and admin CRUD orchestration
    • bird-agent/promotions/router.py app-facing and admin-facing promotion HTTP routes

    Nearby Bird Alerts¶

    • bird-agent/nearby_bird_alerts/tasks.py clustered lookup scheduling, species-difference processing, and due outbox delivery
    • bird-agent/nearby_bird_alerts/outbox.py versioned payload serialization and deterministic email deduplication keys
    • bird-agent/nearby_bird_alerts/notifications.py push, email, and webhook channel adapters with provider-result classification

    The nearby-alert path separates durable discovery state from email-provider delivery. Newly discovered species are recorded once, email work is enqueued with a unique deduplication key, and retryable failures remain eligible for a later worker pass.

    Stage 3 Likelihood Data Engineering¶

    • bird-agent/likelihood/stage3_ebd_backfill.py complete-checklist cohort selection, ecological evidence queries, stratified hard-negative sampling, feature materialization, and resumable checkpoints
    • bird-agent/scripts/backfill_bird_likelihood_stage3_from_ebd.py reproducible CLI controls and phase-level execution summaries

    The backfill contract selects whole checklists through deterministic hash buckets. It commits at checklist boundaries so interrupted runs can skip fully completed events without creating partial label groups.

    API Transport Packages¶

    • bird-agent/rag_api/router.py bird Q&A and RAG rebuild endpoints
    • bird-agent/media_api/router.py image/audio upload and bird-image identification endpoints
    • bird-agent/system_api/router.py root and health endpoints

    Function and Request Flow Diagram¶

    The backend function flow now looks like this:

    flowchart TD

    B --> C["Auth dependency<br/>get_current_user / get_current_registered_user / get_current_admin_user"]
    B --> D["Service module<br/>workflow + orchestration"]
    D --> E["Repository module<br/>SQL only"]
    E --> F["DB connection<br/>app_db.connection.get_connection"]
    D --> G["Shared helpers<br/>serializers / media / moderation.helpers / species.service"]
    G --> H["External systems<br/>Firebase / Firestore / GCS / AI inference / RAG providers"]
    F --> I["SQLite or PostgresCompat"]

    Startup and Lifespan Flow¶

    The backend no longer uses the deprecated @app.on_event("startup") model. It now uses a FastAPI lifespan function.

    sequenceDiagram
    participant Main as main.py
    participant Factory as app_factory.create_app
    participant Life as app_lifespan
    participant DB as app_db.bootstrap
    participant Media as media.py
    participant RAG as rag.py
    participant Detox as moderation.helpers

    Main->>Factory: create_app()
    Factory->>Life: register lifespan
    Life->>DB: initialize_database_if_needed(...)
    Life->>Media: get_firebase_bucket()
    Life->>RAG: prewarm_local_semantic_cache(...)
    Life->>RAG: warmup_ollama_chat_model()
    Life->>Detox: get_detoxify_model()
    Life-->>Factory: yield app runtime

    • bird-agent/moderation/helpers.py
    • policy/state/SLA logic remains isolated in:

    Operationally, this means media cleanup is now a reusable backend concern rather than being duplicated across route handlers.

    Full Test Harness¶

    The current backend test harness is made of four cooperating parts:

    In this codebase, the test harness means the full supporting test infrastructure around the actual test cases.

    It is not just the test_*.py files.

    It includes:

    • the pytest bootstrap and import setup
    • fake connections and in-memory databases
    • shared TestClient builders
    • dependency stubs for Firebase, media, and RAG imports
    • the conventions that let router, service, repository, and app-composition tests run reliably and independently

    The purpose of the harness is to give each test layer the right execution environment:

    • router tests should feel like HTTP requests, not database tests
    • service tests should feel like business-rule tests, not Firebase or SQL integration tests
    • repository tests should execute real SQL, but only against small isolated temporary databases
    • app-composition tests should verify FastAPI wiring and lifecycle behavior without depending on live cloud services or model runtimes

    So when we say “full test harness,” we mean the reusable Python testing infrastructure that makes the layered suite possible and stable.

    1. Import bootstrap and environment isolation¶

    • bird-agent/tests/conftest.py

    This file provides:

    • project-root path bootstrapping for pytest
    • lightweight fake connection objects for service tests
    • in-memory SQLite connections for repository tests
    • import-time stubs for external dependency chains such as:
    • media
    • auth.service
    • firebase_admin
    • rag
    • ai.bird_image_identifier

    This is important because focused unit tests should validate backend logic, not fail during collection because Firebase, cryptography, or model runtimes are unavailable locally.

    2. Router test utility¶

    • bird-agent/tests/test_utils.py

    This utility provides a reusable FastAPI + TestClient wrapper for router tests, including dependency overrides. It keeps API tests small and consistent.

    3. Service harness¶

    Service tests use:

    • fake connection objects
    • monkeypatched repository calls
    • monkeypatched helper functions

    This lets the tests verify:

    • validation flow
    • workflow branching
    • transaction boundaries
    • side-effect orchestration

    without depending on a real database.

    4. Repository harness¶

    Repository tests use:

    • temporary in-memory SQLite databases
    • minimal per-test schema setup
    • real SQL execution through the repository functions

    This lets the tests verify:

    • query correctness
    • join behavior
    • aggregate behavior
    • update/delete semantics
    • SQLite-specific edge cases such as INSERT OR IGNORE and lastrowid

    5. App composition harness¶

    App composition tests use:

    • TestClient(create_app())
    • monkeypatched startup collaborators
    • import-time stubs for Firebase/media/RAG dependencies

    This verifies:

    • route registration
    • middleware registration
    • startup/lifespan orchestration
    • app-level wiring independent of individual endpoint behavior

    Practical Outcome of the Refactor¶

    The backend is no longer a single giant script-style application file.

    It now has:

    • a thin ASGI entrypoint
    • an app factory with lifespan-managed startup
    • domain routers
    • service orchestration modules
    • repository-backed SQL boundaries
    • layered tests for composition, HTTP, workflow, and SQL

    That is a materially better Python backend foundation for future work such as:

    • deeper Postgres migration
    • more AI providers
    • background job extraction
    • stricter moderation workflows
    • fuller admin tooling
