    Database Schema¶

    This project keeps its primary application database in PostgreSQL.

    The production backend connects through DATABASE_URL, and the tables described here represent the application schema used by the API.

    The current Postgres application tables are:

    • users
    • bird_species
    • predictions
    • ebird_observations
    • ebd_observations_raw
    • bird_likelihood_training_examples
    • bird_likelihood_models
    • bird_community_details
    • bird_detail
    • community_bird_images
    • community_prediction_ratings
    • community_prediction_reactions

    Schema Layers¶

    The schema falls into a few functional layers:

    • Core app data: users, bird_species, predictions, bird_detail
    • Community and moderation: community_*, user_blocks, trust_safety_actions, user_safety_signals
    • Support and admin operations: user_feedback*, site_config, report_type, sla_policy, escalation_rule, audit_log
    • Media and retrieval: bird_species_sound_*, bird_species_rag_embeddings, bird_species_local_semantic_embeddings
    • Promotions: promotions, user_promotion_state
    • Nearby alerts: per-user scheduling fields, channel preferences, user_seen_species, and notification_outbox
    • Likelihood / EBD / ML: ebird_observations, ebd_observations_raw, bird_likelihood_training_examples, bird_likelihood_models

    users is the account table for authenticated, guest, and admin users.

    It is referenced throughout the app by predictions, community actions, support flows, moderation, and promotions.

    email TEXT Unique account email
    firebase_uid TEXT Linked Firebase Auth user id
    display_name TEXT Public display name
    avatar_url TEXT Avatar image URL
    bio TEXT Optional profile bio
    password_hash TEXT Local password hash if using local auth
    auth_provider TEXT Auth source such as local or Firebase-backed flows
    provider_subject TEXT Upstream provider subject
    role TEXT Role such as user or admin
    is_active INTEGER 0/1 account activation flag
    is_guest INTEGER 0/1 guest-account flag
    email_verified INTEGER 0/1 verification flag
    push_notifications_enabled BOOLEAN Whether nearby-alert push delivery is enabled
    email_notifications_enabled BOOLEAN Whether nearby-alert email delivery is enabled
    last_login_at TEXT Last login timestamp
    created_at TEXT Timestamp
    updated_at TEXT Timestamp

    bird_detail¶

    bird_detail now acts as the ordered species image gallery table.

    This is the source of truth for all admin-managed species images.

    Column Type Description
    id INTEGER Primary key
    bird_species_id INTEGER Foreign key to bird_species
    image_url TEXT Species image storage path, usually species/...
    song_audio_url TEXT Legacy/unused extra media column still present in schema
    display_order INTEGER Gallery order for the species, lower values shown first
    image_quality INTEGER Training/display usefulness score used by gallery and training tools
    source_name TEXT Upstream image source such as avicommons, wikimedia-commons, dropbox, or synced-gallery
    source_record_id TEXT Source-specific identifier such as an Avicommons code:key pair or a filename/title
    managed_by TEXT Owning automation for refreshable gallery rows
    managed_rank INTEGER Intended order inside a managed gallery block
    is_managed INTEGER 0/1 flag indicating whether automation owns the row lifecycle

    Important rule¶

    For each species:

    • the selected bird_species.default_image_url should also exist as one of that species’s bird_detail.image_url rows
    • admin reordering is stored in bird_detail.display_order
    • backend reads gallery images with:
    • ORDER BY display_order ASC, id ASC
    • current Avicommons gallery refreshes mark their rows with:
    • managed_by = 'download_avicommons_thumbnails'
    • is_managed = 1
    • managed_rank = 1..N
    • stale managed thumbnail rows are currently demoted to the end of the gallery instead of being deleted

    That means:

    • bird_species.default_image_url is the chosen default image pointer
    • bird_detail is the ordered gallery
    • bird_detail also carries provenance and management metadata for gallery refresh tooling

    Likelihood And EBD Tables¶

    These tables support the bird-likelihood pipeline and the additive EBD import path.

    They are intentionally separate because they serve different jobs:

    • ebird_observations is the compact runtime evidence store used by the app
    • ebd_observations_raw is the richer near-raw landing table for bulk EBD extracts
    • bird_likelihood_training_examples is the materialized ML-ready feature/label table
    • bird_likelihood_models is the model registry

    ebird_observations¶

    ebird_observations is the compact historical bird-evidence table used by likelihood scoring and related product lookups.

    This is the operational table the live app can query safely at serving time.

    Column Type Description
    id INTEGER Primary key
    species_code TEXT eBird species code
    common_name TEXT Common bird name
    scientific_name TEXT Scientific name
    observation_date DATE Observation date
    latitude REAL Observation latitude
    longitude REAL Observation longitude
    location_name TEXT Free-text location label
    observation_count TEXT Count text from source row
    source TEXT Evidence source, default ebird
    imported_at TEXT Import timestamp

    Used for:

    • live bird-likelihood evidence lookup
    • recent historical density and recency features
    • compact serving-time bird occurrence context

    ebd_observations_raw¶

    ebd_observations_raw is the additive near-raw monthly EBD landing table.

    This table preserves checklist/event metadata that would be too heavy or too detailed for the compact runtime table.

    It is primarily a staging, analytics, and offline-ML source table.

    Column group Examples What it is used for
    Bird identity taxon_concept_id, common_name, scientific_name, subspecies columns Species identity and taxonomy joins
    Count / breeding / behavior observation_count_text, observation_count, breeding_code, behavior_code, age_sex Richer ecological and training features
    Geography country, state, county, iba_code, bcr_code, locality, latitude, longitude Spatial filtering and feature engineering
    Checklist metadata sampling_event_identifier, protocol_name, duration_minutes, effort_distance_km, number_observers, all_species_reported Complete-checklist negatives and effort-aware modeling
    Moderation / quality approved, reviewed, reason Filtering to trustworthy rows
    Comments / payload checklist_comments, species_comments, raw_payload_json Forensics, debugging, and future feature extraction
    Import lineage source_file, source_line_number, imported_at Traceability and reruns

    Important columns:

    • global_unique_identifier uniquely identifies the raw row
    • all_species_reported tells us whether the checklist was complete
    • sampling_event_identifier groups rows by checklist/event
    • approved and reviewed help filter lower-trust records

    Used for:

    • bulk EBD import storage
    • offline analytics
    • Stage 3 feature generation
    • checklist-aware negative example generation
    • re-materializing compact ebird_observations

    bird_likelihood_training_examples¶

    bird_likelihood_training_examples stores materialized supervised-learning rows for Stage 3 bird-likelihood modeling.

    Each row is an ML-ready example rather than a raw observation row.

    Column Type Description
    id INTEGER Primary key
    source_observation_id INTEGER Linked compact source observation when available
    species_id INTEGER Foreign key to bird_species
    example_key TEXT Unique training example id
    label_present INTEGER Supervised target, 1 present or 0 absent
    split_bucket TEXT Dataset split such as train, validation, or test
    feature_version TEXT Feature-set version
    species_name TEXT Species label text
    observation_date TEXT Effective example date
    latitude REAL Feature latitude
    longitude REAL Feature longitude
    radius_km REAL Spatial aggregation radius
    lookback_days INTEGER Main lookback window
    recent_window_days INTEGER Recent evidence window
    historical_lookback_days INTEGER Long historical window
    ebird_sightings_count INTEGER Compact eBird evidence count
    community_sightings_count INTEGER Community evidence count
    user_sightings_count INTEGER User-specific evidence count
    recent_sightings_count INTEGER Recent sightings count
    nearest_sighting_km REAL Distance to nearest matching sighting
    last_seen_days_ago INTEGER Days since last matching sighting
    historical_month_matches INTEGER Same-season evidence count
    historical_total_matches INTEGER All-history evidence count
    season_score INTEGER Seasonal score
    Probability feature columns REAL Precomputed feature probabilities such as recent_probability, distance_probability, season_probability
    metadata_json TEXT Structured provenance and feature metadata
    created_at TEXT Timestamp
    updated_at TEXT Timestamp

    Used for:

    • Stage 3 classifier training
    • evaluation / offline validation
    • model reproducibility by feature_version
    • checklist-aware positive/negative example materialization

    For complete-checklist feature contracts, checklist identity is retained in the metadata payload. Deterministic sampling selects whole checklist events, and resumable backfills treat the presence of an already committed checklist identifier as a durable completion checkpoint.

    The newer hard-negative contract records both its sampling contract and the selected ecological stratum. Candidate selection rotates deterministically across:

    • recent local presence;
    • historical local presence in the same season;
    • historical regional presence in the same season.

    This produces more informative negative examples than arbitrary absent species while preserving reproducibility across reruns.

    bird_likelihood_models¶

    bird_likelihood_models is the Stage 3 model registry.

    It stores metadata about trained models and their artifacts rather than the raw training data itself.

    Column Type Description
    id INTEGER Primary key
    model_key TEXT Unique model identifier
    model_stage TEXT Stage label, default stage_3_ml
    feature_version TEXT Feature-set version the model was trained on
    algorithm TEXT Model family such as gradient boosting or logistic regression
    model_version TEXT Human/model build version
    artifact_path TEXT Path to persisted model artifact
    training_started_at TEXT Training start timestamp
    trained_at TEXT Training completion timestamp
    metrics_json TEXT Serialized evaluation metrics
    params_json TEXT Serialized hyperparameters
    training_row_count INTEGER Number of training rows used
    is_active INTEGER 0/1 active model flag
    notes TEXT Free-form notes
    created_at TEXT Timestamp
    updated_at TEXT Timestamp

    Used for:

    • model artifact registration
    • activation / rollback of trained models
    • offline experiment tracking
    • evaluation-history auditability

    Nearby Alert Delivery Tables¶

    notification_outbox¶

    notification_outbox stores durable nearby-alert email work separately from species-discovery state.

    Column Type Description
    id BIGINT Primary key
    user_id BIGINT Recipient account
    channel TEXT Delivery channel, currently used for durable email work
    destination TEXT Destination captured for the delivery attempt
    event_type TEXT Notification event classification
    deduplication_key TEXT Unique content-derived key preventing duplicate enqueueing
    payload JSON Versioned serialized sighting payload
    status TEXT Pending, processing, accepted, or classified failure state
    attempt_count INTEGER Number of provider attempts
    next_attempt_at TIMESTAMP Earliest retry time
    provider_message_id TEXT Provider acceptance identifier when available
    last_error_code TEXT Safe machine-readable failure classification
    last_error_message TEXT Sanitized operational failure detail
    accepted_at TIMESTAMP Provider-acceptance timestamp
    created_at TIMESTAMP Creation timestamp
    updated_at TIMESTAMP Last state-change timestamp

    The unique deduplication key makes enqueueing idempotent. Indexed status and retry timestamps allow workers to claim due work without scanning completed delivery history.

    Community Bird Contribution Tables¶

    bird_community_details¶

    bird_community_details stores user-submitted species-enrichment content waiting for or passing moderation.

    It is separate from canonical bird_species so community contributions can be reviewed before being merged or surfaced.

    community_bird_images¶

    community_bird_images stores user-submitted bird images linked to bird_community_details.

    It preserves attribution, moderation state, ordering, and default-image selection for community-supplied media.

    community_prediction_ratings¶

    Stores one star rating per user, per shared prediction.

    Column Type Description
    id INTEGER Primary key
    prediction_id INTEGER Shared prediction id
    user_id INTEGER Rating user id
    rating INTEGER 1-5 star rating
    created_at TEXT Timestamp
    updated_at TEXT Timestamp

    Important index:

    • unique (prediction_id, user_id)

    community_prediction_reactions¶

    Stores one thumbs reaction per user, per shared prediction.

    Column Type Description
    id INTEGER Primary key
    prediction_id INTEGER Shared prediction id
    user_id INTEGER Reacting user id
    reaction INTEGER 1 for upvote, -1 for downvote
    created_at TEXT Timestamp
    updated_at TEXT Timestamp

    Important index:

    • unique (prediction_id, user_id)

    community_prediction_comments¶

    Stores comments on shared predictions.

    Column Type Description
    id INTEGER Primary key
    prediction_id INTEGER Shared prediction id
    user_id INTEGER Comment author id
    body TEXT Comment text
    created_at TEXT Timestamp
    updated_at TEXT Timestamp

    Important read pattern:

    • comments are queried by prediction_id, newest first

    community_reports¶

    Stores moderation reports for community posts, comments, and users.

    Column Type Description

    prediction_id INTEGER Optional reported prediction id
    comment_id INTEGER Optional reported comment id
    reported_user_id INTEGER Optional reported user id
    report_lane TEXT Explicit lane such as report_content or report_user
    reason TEXT Short machine-readable or user-supplied report reason
    details TEXT Optional free-text explanation
    status TEXT Review state such as open, reviewing, resolved, dismissed
    workflow_stage TEXT Moderation stage such as ticket_created, notification_sent, or reporter_follow_up
    priority TEXT Human triage priority such as low, medium, or high
    severity_label TEXT Auto-classified severity such as low, medium, high, or critical
    severity_score REAL Numeric severity score used with severity_label
    outcome TEXT Resolution outcome such as action_taken or no_action
    content_action_type TEXT Content-level action such as content_removed, content_hidden, warning_only, or no_content_action
    trust_safety_action_type TEXT Case-level trust decision such as warn, temporary_suspend, permanent_ban, or no_trust_action
    ticket_ack_message TEXT Initial user-facing acknowledgement message
    admin_user_id INTEGER Admin who last reviewed the report
    admin_note TEXT Internal review / moderation note
    admin_reply TEXT Moderator-facing or reporter-facing reply content used in the review flow
    user_response TEXT Reporter follow-up after a moderation decision
    user_responded_at TEXT Timestamp of the reporter follow-up
    decision_note TEXT Policy decision summary
    enforcement_note TEXT Enforcement summary text
    notification_message TEXT Final notification text
    reporter_notified_at TEXT Timestamp when the reporter was notified
    reported_user_notified_at TEXT Timestamp when the reported user was notified
    auto_classified_at TEXT Timestamp when severity classification was stamped
    created_at TEXT Timestamp
    reviewed_at TEXT Timestamp of the latest review
    updated_at TEXT Timestamp

    Important indexes:

    • (status, created_at, id)
    • (reporter_user_id, created_at, id)
    • (report_lane, created_at, id)
    • (reported_user_id, created_at, id)

    user_blocks¶

    Stores one-way user block relationships used by the community feed and interaction rules.

    Column Type Description
    id INTEGER Primary key
    blocker_user_id INTEGER User who initiated the block
    blocked_user_id INTEGER User being blocked
    created_at TEXT Timestamp

    Important indexes:

    • unique (blocker_user_id, blocked_user_id)
    • index on (blocked_user_id, blocker_user_id)

    user_feedback¶

    Stores the support ticket header for user/admin communication.

    This table is the persistent source of truth for user/admin communication.

    • the phone is only a client view of the conversation
    • the original user ticket text is still mirrored in message
    • the latest admin reply is still mirrored in admin_response
    • the responding admin is tracked in admin_user_id
    • the full conversation now lives in user_feedback_messages
    • Firebase Auth is used only to verify identity before the backend writes or returns feedback data

    So the feedback thread itself is not stored locally on the phone and is not stored in Firebase as the main record.

    Column Type Description
    id INTEGER Primary key
    user_id INTEGER Feedback author
    subject TEXT Optional short subject line
    message TEXT Original ticket body
    status TEXT Ticket state such as waiting_on_admin, waiting_on_user, closed_by_user, or resolved
    admin_response TEXT Latest mirrored admin reply text
    admin_user_id INTEGER Admin who replied
    sentiment_label TEXT Optional sentiment or tone classification
    sentiment_score REAL Optional numeric sentiment score
    created_at TEXT Timestamp
    responded_at TEXT Timestamp when the admin replied
    last_message_at TEXT Timestamp of the latest thread message
    resolved_at TEXT Timestamp when the ticket was resolved
    updated_at TEXT Timestamp

    user_feedback_messages¶

    Stores the actual support thread messages linked to user_feedback.

    Column Type Description
    id INTEGER Primary key
    feedback_id INTEGER Parent support ticket id
    author_user_id INTEGER Optional user/admin id of the message author
    author_role TEXT user or admin
    message TEXT Message body
    created_at TEXT Timestamp

    trust_safety_actions¶

    Stores account-level enforcement actions attached to report_user cases.

    Column Type Description
    id INTEGER Primary key
    report_id INTEGER Linked community_reports row
    reported_user_id INTEGER User account the action applies to
    action_type TEXT warn, temporary_suspend, or permanent_ban
    duration_hours INTEGER Optional duration for temporary suspensions
    starts_at TEXT Action start timestamp
    ends_at TEXT Optional end timestamp
    reason TEXT Human-authored enforcement reasoning
    created_by_admin_user_id INTEGER Admin who created the action
    created_at TEXT Timestamp

    user_safety_signals¶

    Stores derived safety signals used to understand repeated or escalating behaviour across moderation and block flows.

    Column Type Description
    id INTEGER Primary key
    user_id INTEGER User the signal is about
    signal_type TEXT Signal such as reported_content, reported_user, blocked_by_user, or trust-action-derived values
    source_table TEXT Source table such as community_reports, user_blocks, or trust_safety_actions
    source_record_id INTEGER Optional linked row id in the source table
    weight REAL Numeric weight used for risk-style aggregation
    metadata_json TEXT Optional structured metadata for the signal
    created_at TEXT Timestamp

    bird_species_rag_embeddings¶

    Caches embedding rows for the optional OpenAI retrieval path of the bird Q&A feature.

    Column Type Description
    id INTEGER Primary key
    bird_species_id INTEGER Source species id
    content_hash TEXT Hash of the source searchable document
    embedding_model TEXT Embedding model name
    embedding_json TEXT Serialized vector
    source_text TEXT Searchable species document
    created_at TEXT Timestamp
    updated_at TEXT Timestamp

    bird_species_local_semantic_embeddings¶

    Stores locally computed semantic embeddings for the non-OpenAI retrieval path.

    This is the local-embedding companion to bird_species_rag_embeddings.

    bird_species_sound_sources¶

    This table is the current sound-ingestion source of truth.

    Purpose:

    • keep full source attribution and license data per recording
    • store more than one candidate recording per species
    • separate the selected app-facing song / call pointers from the larger source archive

    bird_species.song_audio_url and bird_species.call_audio_url remain the selected playback fields, while bird_species_sound_sources is the ingestion and retrieval source of truth.

    Column Type Description
    id INTEGER Primary key
    bird_species_id INTEGER Foreign key to bird_species
    source_name TEXT Usually xeno-canto
    source_recording_id TEXT Source recording id
    source_page_url TEXT Public source page URL
    download_url TEXT Original downloadable audio URL
    storage_path TEXT Stored local or cloud storage path
    audio_role TEXT song, call, training_song, or definitive
    license_name TEXT Source license text
    recordist TEXT Attribution name
    quality_grade TEXT Quality label such as A / B
    recording_type TEXT song, alarm call, flight call, etc
    country TEXT Recording country
    location TEXT Free-text location
    recorded_at TEXT Date/time text if available
    duration_seconds REAL Audio duration
    remarks TEXT Recordist notes
    background_species TEXT Other species present
    channels INTEGER Mono/stereo channel count
    sample_rate_hz INTEGER Sampling rate
    is_selected INTEGER 0/1 chosen exemplar marker
    created_at TEXT Timestamp
    updated_at TEXT Timestamp

    Current indexes in the verified schema:

    • unique (source_name, source_recording_id, audio_role)
    • index on (bird_species_id, audio_role)
    • index on (bird_species_id, is_selected)

    Current relationship:

    • one bird_species row can have many bird_species_sound_sources

    bird_species_sound_ingestion_status¶

    Tracks the current ingestion state for each species in the sound-pipeline workflow.

    Used for:

    • knowing whether a species still needs sound ingestion
    • surfacing ingestion failures and retry reasons
    • preventing duplicate ingestion work

    Promotions Tables¶

    promotions¶

    Stores admin-managed promotional cards or banners shown in the app.

    Used for:

    • scheduled promotional campaigns
    • active/inactive app messaging
    • priority-ordered display logic

    user_promotion_state¶

    Stores per-user interaction state for each promotion.

    Used for:

    • throttling repeat display
    • recording dismiss / click / show counts
    • personalization of promo display frequency

    Admin, Support, And Governance Tables¶

    user_feedback_status_history¶

    Stores the full status-transition history for a support ticket in user_feedback.

    site_config¶

    Stores editable application configuration values and admin-tunable runtime settings.

    report_type¶

    Stores the catalog of moderation/support report types.

    sla_policy¶

    Stores SLA timing rules by report type and priority.

    escalation_rule¶

    Stores rule-based escalation logic for report handling.

    audit_log¶

    Stores append-only record-level audit information for tracked admin changes.

    Image Management Model¶

    The current admin image-management model works like this:

    1. all manageable species images live in bird_detail
    2. image order is stored in bird_detail.display_order
    3. the selected default image is stored in bird_species.default_image_url
    4. the default image should be one of that species’s bird_detail.image_url values
    5. rows are never deleted just to hide them from the gallery UI

    Current gallery visibility rule:

    • rows with display_order < 999 are treated as visible gallery images
    • rows with display_order = 999 are treated as hidden from the gallery
    • hidden rows still remain in bird_detail
    • hidden rows are still available in richer API payloads for future screens or admin tooling

    Backend admin endpoints that operate on this model:

    • GET /admin/species
    • GET /admin/species/{species_id}/images
    • PATCH /admin/species/{species_id}/default-image
    • PATCH /admin/species/{species_id}/image-order

    Media Path Notes¶

    • migrated species media is stored in the application database as stable storage paths instead of local /uploads/... URLs
    • the backend signs those paths at response time before returning them to the app or admin website
    • some older prediction rows may still contain already-signed cloud URLs, which the backend passes through as-is
    • predictions.audio_url is used by Add Prediction, Update Prediction, and prediction-detail playback flows

    Current Read Behavior¶

    The app and admin website currently rely on these rules:

    • Bird List thumbnails use bird_species.default_image_url
    • Bird Detail hero image uses bird_species.default_image_url unless a prediction-specific image is present
    • community detail also prefers prediction-specific images first
    • Bird Detail gallery uses only visible bird_detail rows ordered by display_order
    • hidden gallery rows (display_order = 999) are excluded from additional_image_urls
    • richer image metadata is now also available via additional_image_items
    • the admin website edits:
    • bird_species.default_image_url
    • bird_detail.display_order

    Admin-web gallery behavior:

    • Remove on an image row sets that row to the hidden-gallery state
    • Restore moves that row back into the visible ordered set
    • save writes:
    • contiguous 0..N orders for visible rows
    • 999 for hidden rows
    • this is a hide/unhide workflow, not a delete workflow

    Community Data Rules¶

    • community state is layered on top of predictions, not stored as a separate post table
    • unsharing a prediction clears its community visibility flags without deleting the prediction row
    • deleting a prediction removes its attached community ratings, reactions, and comments
    • community rating/reaction/comment tables are only meaningful for predictions where shared_to_community = 1

    Bird Q&A Source Data¶

    • bird_species is also the source table for the bird-question retrieval corpus
    • the new extended descriptive fields can improve local matching and OpenAI embedding quality when populated
