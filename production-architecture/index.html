    Production Architecture¶

    This page documents the deployed production architecture and the controlled scaling path for Spark Birds. Local development retains compatible service boundaries so application behaviour can be validated before release.

    If you want the concrete server checklist and file layout, use:

    • remote-server-setup.md

    It is written for the current repo shape:

    • Expo / React Native mobile app
    • FastAPI backend in bird-agent
    • PostgreSQL production database
    • Redis-backed task coordination and caching
    • Firebase Storage for media
    • versioned PyTorch classifier artifacts and LightGBM likelihood models

    The goal is:

    • efficient infrastructure use
    • simple operations
    • easy model updates
    • room to grow later

    Current Production Shape¶

    The current efficient production setup is:

    1. run the FastAPI API and background workers on a Hetzner Linux host
    2. use PostgreSQL as the transactional application database
    3. use Redis for nearby-alert scheduling and shared external-data caching
    4. keep media in Firebase/GCS and return signed URLs through the API
    5. load versioned model artifacts on the backend so model promotion is independent of App Store releases

    Deployed layout¶

    flowchart LR User["App Store user"] --> App["Spark Birds
    Expo / React Native"] App --> Edge["HTTPS / Nginx"] Edge --> API["FastAPI application service"] API --> DB["PostgreSQL"] API --> Media["Firebase / GCS media"] API --> Models["Versioned image and
    likelihood model artifacts"] API --> Redis["Redis cache and task coordination"] Redis --> Workers["Celery workers and schedules"] Workers --> DB

    Efficient Infrastructure Recommendation¶

    The deployed one-box topology intentionally uses:

    • one backend service
    • one PostgreSQL database host
    • Firebase/GCS object storage
    • separately supervised API, worker, scheduler, and refresh services

    Deployment topology¶

    • a suitably sized Hetzner VM for bird-agent
    • Firebase Storage for media
    • PostgreSQL for transactional and workflow state
    • Nginx for HTTPS termination and reverse proxying
    • systemd for service supervision

    This is more operationally efficient than prematurely introducing:

    • trying to run inference on phones
    • adding separate vector databases
    • adding Kubernetes
    • adding multiple always-on backend services

    Why The Backend Should Run The Models¶

    The current model artifacts are:

    • bird-agent/models/bird-image-model.pt
    • current local training output:
    • /Volumes/DATA/models/bird-sound-model.pt
    • typical production target path:
    • /opt/bird-platform/models/bird-image-model.pt
    • typical production target path:
    • /opt/bird-platform/models/bird-sound-model.pt

    Those are best treated as backend-loaded artifacts.

    Reasons:

    • easiest deployment path
    • no model conversion needed for mobile
    • simpler updates
    • one model version for all users
    • no app-store release needed when the model changes

    Inference flow¶

    sequenceDiagram participant User participant App participant API as FastAPI backend participant Model as .pt model artifact participant DB as PostgreSQL User->>App: Submit image or sound App->>API: POST request with media or media path API->>Model: Load artifact and run inference Model-->>API: Ranked species predictions API->>DB: Load species metadata DB-->>API: Species rows API-->>App: Prediction JSON

    Suitable Hosting Options¶

    Current option: Small VM¶

    Examples:

    • Hetzner cloud VM
    • DigitalOcean Droplet
    • AWS EC2 small instance

    Why it fits:

    • efficient and predictable always-on option in many cases
    • easy to store .pt files on local disk
    • easy to run FastAPI with one process manager
    • supports the current PostgreSQL, Redis, worker, and model-serving topology

    Tradeoffs:

    • you manage more of the server yourself
    • OS patching and service restarts are your responsibility

    Option B: Simple app platform¶

    Examples:

    • Render
    • Railway
    • Fly.io

    Why it fits:

    • easier deployment than a raw VM
    • logs and restarts are simpler
    • good if you want less server management

    Tradeoffs:

    • often more expensive than a minimal VM deployment
    • persistent disk and model file handling need more care
    • SQLite can be awkward on some platforms

    Repository Deployment Model¶

    The repository's current deployment model is:

    • backend:
    • one small Linux VM
    • API:
    • run bird-agent with uvicorn behind a reverse proxy
    • DB:
    • PostgreSQL with Alembic-owned schema migration
    • media:
    • Firebase Storage
    • model files:
    • store on the server disk

    This gives you:

    • the lowest moving-part count
    • simple model loading
    • lower operational overhead than managed multi-service setups

    Database Architecture¶

    Production: PostgreSQL¶

    PostgreSQL is the production source of truth for:

    • user and species data
    • sightings, predictions, and community workflows
    • moderation, support, promotions, and entitlements
    • model registry and contextual likelihood data
    • durable notification delivery state

    Alembic owns production schema evolution. CI validates migrations against an isolated PostgreSQL service before changes can be merged.

    Development and compatibility use¶

    Some ingestion utilities, tests, and legacy compatibility paths can still use SQLite-oriented assets. They are not the production application database and must not be treated as the authoritative deployment schema.

    Media Recommendation¶

    Use Firebase Storage for:

    • species images
    • species sounds
    • uploaded prediction images
    • uploaded prediction audio

    Do not use Firebase Storage as the thing that runs inference.

    Instead:

    • Firebase stores files
    • bird-agent reads file paths or signed URLs
    • bird-agent runs the model

    Media flow¶

    flowchart TD App["Mobile app"] --> Upload["Upload image/audio"] Upload --> Firebase["Firebase Storage"] Firebase --> API["FastAPI backend"] API --> Predict["Model inference"] Predict --> App

    Model Artifact Placement¶

    For efficient model delivery, store the model artifacts either:

    • directly on the backend server disk
    • or in cheap object storage, downloaded by the backend at startup

    Best first choice¶

    • keep .pt files on the backend server disk

    Why:

    • simplest startup
    • fastest runtime access
    • no extra download logic required

    Example production file layout¶

    /opt/bird-platform/
  app/
    bird-agent/
  data/
    birds.db
  models/
    bird-image-model.pt
    bird-sound-model.pt

    Image Identification In Production¶

    This can stay very close to the current setup.

    flowchart TD A["Phone uploads image"] --> B["bird-agent API"] B --> C["Load bird-image-model.pt"] C --> D["Run image classifier"] D --> E["Map class to bird_species row"] E --> F["Return ranked predictions"]

    Sound Identification In Production¶

    This should also stay backend-side.

    flowchart TD A["Phone uploads sound"] --> B["bird-agent API"] B --> C["Load bird-sound-model.pt"] C --> D["Preprocess audio"] D --> E["Run sound classifier"] E --> F["Map class to bird_species row"] F --> G["Return ranked predictions"]

    Bird Q&A In Production¶

    For an efficient default production configuration, the recommendation is:

    • local retrieval
    • local answer builder
    • OpenAI only when you explicitly want the improved answer quality

    Recommended configuration¶

    BIRD_RAG_RETRIEVAL_PROVIDER=local
BIRD_RAG_ANSWER_PROVIDER=local

    Why:

    • no per-request OpenAI cost
    • no dependency on embedding refresh jobs
    • no quota concerns

    If you later enable OpenAI, do it deliberately and only for the Q&A feature, not as a default dependency for the whole app.

    Controlled Scaling Phases¶

    Phase 1: Current production baseline¶

    • one Hetzner backend host
    • PostgreSQL
    • Redis and supervised background workers
    • Firebase Storage
    • versioned model files on backend disk
    • configured local or hosted RAG providers

    Phase 2: Better reliability¶

    • move PostgreSQL and Redis to isolated managed or dedicated hosts when load or recovery requirements justify it
    • keep one application host or scale cautiously
    • keep model inference on backend

    Phase 3: Higher scale¶

    • multiple backend instances
    • managed Postgres
    • better job scheduling
    • stronger monitoring

    Deferred Scaling Decisions¶

    These components are deferred until measured load or reliability requirements justify their operational cost:

    • on-device sound/image inference
    • vector database hosting
    • Kubernetes
    • multiple microservices
    • separate model-serving infrastructure
    • managed GPU inference unless traffic truly requires it

    Production Environment Variables¶

    Typical production env will still include the current themes:

    • API secrets / JWT settings
    • Firebase storage config
    • optional OpenAI key for bird Q&A only
    • model paths

    Example shape:

    DATABASE_URL=postgresql://birdplatform:YOUR_PASSWORD@127.0.0.1:5432/bird_platform
FIREBASE_STORAGE_BUCKET=your-project.firebasestorage.app
FIREBASE_PREDICTION_STORAGE_BUCKET=your-project.firebasestorage.app
BIRD_RAG_RETRIEVAL_PROVIDER=local
BIRD_RAG_ANSWER_PROVIDER=local
BIRD_IMAGE_MODEL_PATH=/opt/bird-platform/models/bird-image-model.pt
BIRD_SOUND_MODEL_PATH=/opt/bird-platform/models/bird-sound-model.pt

    Operational Recommendation¶

    For the current production release:

    1. deploy bird-agent on one small VM
    2. keep PostgreSQL on the same box for the main app database
    3. keep Firebase Storage for media
    4. load .pt model artifacts from server disk
    5. keep bird Q&A on local providers by default
    6. keep the ingestion and training utilities separate from the live app database where useful

    That is the best fit between:

    • operational efficiency
    • the current repository architecture
    • minimal migration work
    • maintainability
