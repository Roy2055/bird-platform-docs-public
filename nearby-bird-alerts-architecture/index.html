    Nearby Bird Alerts Architecture¶

    This page documents the eBird-powered nearby bird alerts module now integrated into the backend.

    The selected interval controls when a user is eligible for another lookup. It is not a promise that an email or push notification will be sent at every interval: dispatch occurs only when the lookup finds a species code that is not already present in that user's seen-species history.

    It is designed as a scalable sidecar domain inside bird-agent, with its own:

    • configuration
    • PostgreSQL tables
    • Redis-backed cache and task queue
    • Celery scheduler and workers
    • notification dispatcher

    The current implementation lives in:

    • bird-agent/nearby_bird_alerts

    App Flow¶

    The app now uses a dedicated AI Bird Log screen as the control surface for nearby bird alerts and bird questions.

    Current flow:

    • the shared bird icon in the main app header routes to AI Bird Log
    • users save a location, interval, radius, and days-back window there
    • the Map action opens the dedicated sightings screen
    • bird questions live below the nearby alert controls instead of inside a modal
    flowchart TD Header["Bird icon in shared header"] --> Log["AI Bird Log screen"] Log --> Save["Save nearby alert preferences"] Log --> Ask["Ask bird questions"] Save --> Map["Map action"] Map --> Sightings["Dedicated sightings map screen"]

    App Mapping View¶

    The nearby bird alerts flow in the app now opens a dedicated sightings screen that plots three filtered datasets on one shared map:

    • blue pins:
    • You
    • the logged-in user's Bird Platform sightings
    • yellow pins:
    • Other Users
    • community-shared Bird Platform sightings from other users
    • green pins:
    • eBird sightings stored in user_seen_species

    All three datasets are distance-filtered against the saved nearby-alert center before the shared map renders them.

    Current interaction details:

    • AI Bird Log now links to a separate Sightings screen instead of using an embedded modal flow
    • app and community markers render a small circular bird thumbnail when an image URL is available
    • eBird markers still use the color-only fallback because the nearby-alert API does not yet supply species image URLs
    • a floating Show all pins control switches between hotspot focus and the full map point set
    • a tap on the map background dismisses the selected bird detail card
    • the legend is interactive:
    • tapping You, Other Users, or eBird greys that source out and removes those pins from the map

    Radius Distance Math¶

    The app filters all three nearby-map datasets against the saved alert center before rendering pins.

    Inputs:

    • alert center:
    • lat1
    • lng1
    • sighting point:
    • lat2
    • lng2
    • selected radius:
    • radius_km

    Decision rule:

    • include the point when:
    • distance_km <= radius_km
    flowchart TD A["Saved alert center
    lat1, lng1"] --> C["Calculate distance to sighting"] B["Sighting point
    lat2, lng2"] --> C C --> D{"distance_km <= radius_km?"} D -- Yes --> E["Show pin on map"] D -- No --> F["Do not show pin"]
    sequenceDiagram participant Alert as Alert center participant Point as Sighting point participant Math as Haversine math participant Map as Map renderer Alert->>Math: lat1, lng1, radius_km Point->>Math: lat2, lng2 Math-->>Math: compute distance_km alt distance_km <= radius_km Math->>Map: include point else distance_km > radius_km Math->>Map: exclude point end

    The current app uses the Haversine formula:

    function toRadians(value: number) {
  return (value * Math.PI) / 180;
}

function getDistanceKm(
  fromLat: number,
  fromLng: number,
  toLat: number,
  toLng: number
) {
  const earthRadiusKm = 6371;
  const dLat = toRadians(toLat - fromLat);
  const dLng = toRadians(toLng - fromLng);
  const a =
    Math.sin(dLat / 2) * Math.sin(dLat / 2) +
    Math.cos(toRadians(fromLat)) *
      Math.cos(toRadians(toLat)) *
      Math.sin(dLng / 2) *
      Math.sin(dLng / 2);

  return earthRadiusKm * 2 * Math.atan2(Math.sqrt(a), Math.sqrt(1 - a));
}

    This filter is applied to:

    • blue pins:
    • the logged-in user's app sightings
    • yellow pins:
    • other users' community-shared app sightings
    • green pins:
    • eBird nearby sightings

    Purpose¶

    The goal of this module is to notify users only when genuinely new nearby bird sightings appear for them, without making one eBird API call per user.

    Instead, users are grouped into shared location clusters so the system can:

    • reduce external API calls
    • cache repeated lookups
    • diff results against each user's seen-species history
    • notify only the users who have newly relevant sightings

    Per-User Interval Throttling¶

    The worker still wakes up globally, but it no longer processes every active user on every tick.

    Instead:

    • each user stores:
    • check_interval
    • last_checked_at
    • next_check_at
    • the scheduler selects only users whose next_check_at is due
    • it immediately advances that due time before queueing cluster work
    • clustering then runs only across that due slice

    This keeps the implementation efficient because the narrow sample happens in the database query before clustering and eBird fetches.

    flowchart TD Beat["Global beat tick
    every settings.poll_interval_seconds"] --> Due["SELECT users WHERE is_active = true
    AND next_check_at <= now()"] Due --> Claim["FOR UPDATE SKIP LOCKED
    claim due users"] Claim --> Advance["Set last_checked_at = now()
    Set next_check_at = now() + user interval"] Advance --> Cluster["Build clusters from due users only"] Cluster --> EBird["Fetch sightings per cluster"] EBird --> Diff["Diff sightings vs user_seen_species"] Diff --> Notify["Send notifications"]

    Main Components¶

    1. FastAPI Service¶

    The alerts router exposes user registration and preference management endpoints under:

    • /birds/users
    • /birds/users/{external_id}
    • /birds/users/{external_id}/seen
    • /birds/health

    Source:

    • bird-agent/nearby_bird_alerts/api.py

    Responsibilities:

    • register alert users
    • update location and alert preferences
    • persist the app-selected check_interval value for each user
    • seed or reset next_check_at when scheduling-relevant fields change
    • activate/deactivate users
    • inspect and reset seen-species history

    2. PostgreSQL¶

    This module is intentionally Postgres-native.

    It currently stores:

    • users
    • user_seen_species

    Source:

    • bird-agent/nearby_bird_alerts/database.py
    • bird-agent/alembic_nearby_bird_alerts/versions/20260603_0001_create_nearby_bird_alert_tables.py

    The main backend can continue using SQLite during migration, but this module is already separated so it can move cleanly onto Postgres first.

    Current app/API preference fields include:

    • lat
    • lng
    • location_name
    • radius_km
    • days_back
    • max_results
    • check_interval
    • last_checked_at
    • next_check_at
    • email
    • push_token
    • webhook_url
    • is_active

    3. Location Clusterer¶

    The clusterer groups users into shared grid cells using cluster_grid_degrees.

    Source:

    • bird-agent/nearby_bird_alerts/clustering.py

    Why this matters:

    • 10,000 users do not imply 10,000 eBird API calls
    • nearby users can share one lookup
    • cluster centres can reduce the polling workload to roughly tens or low hundreds of API requests, depending on geographic spread

    Notification Channels And Delivery Semantics¶

    The dispatcher supports the destinations saved in the alert profile:

    • Expo push tokens use the Expo Push API;
    • other native push tokens use Firebase Cloud Messaging when server credentials are configured;
    • email uses Resend when selected by configuration, with SMTP available as an alternative;
    • webhook destinations receive an HTTP JSON payload.

    Emails contain plain-text and HTML bodies. A successful provider API response means the provider accepted the request; it should not be interpreted as proof of final inbox or device delivery.

    The implementation uses user_seen_species as its durable, per-user species deduplication record. This prevents a currently visible species from generating a notification on every scheduler pass.

    Push and email preferences are stored independently. Push and webhook adapters remain immediate channel calls, while email uses a PostgreSQL-backed outbox:

    • discovery and email enqueueing commit together;
    • a content-derived unique key prevents duplicate email work;
    • the delivery worker claims pending or retryable rows in bounded batches;
    • network failures, HTTP 408, 429, and server errors receive exponential backoff, capped at one hour and five attempts;
    • non-retryable or exhausted failures are retained as permanent_failed;
    • successful provider acceptance stores the provider message identifier and acceptance timestamp.

    This design preserves a clear distinction between a provider accepting a message and the message reaching an inbox. It also prevents a transient email provider failure from losing the underlying notification event.

    4. eBird Client With Redis Cache¶

    The eBird client performs cluster-level recent-sighting fetches and caches results in Redis.

    Source:

    • bird-agent/nearby_bird_alerts/ebird.py

    Current behavior:

    • cache key based on:
    • lat
    • lng
    • radius
    • days_back
    • max_results
    • default TTL:
    • 240 seconds

    This avoids repeated eBird calls for the same cluster during a short interval.

    5. Celery Beat And Worker Tasks¶

    Source:

    • bird-agent/nearby_bird_alerts/tasks.py

    Three main tasks drive the system:

    • schedule_all_clusters
    • Beat-triggered scheduler
    • check_cluster
    • worker task for one cluster
    • deliver_notification_outbox
    • worker task for due email deliveries and retries

    Flow:

    1. Beat fires on the configured interval
    2. active users whose next_check_at is due are claimed from Postgres
    3. each claimed user's next due time is advanced from their saved interval
    4. due users are grouped into clusters
    5. one check_cluster task is queued per cluster
    6. each cluster lookup diffs against each user's seen history
    7. new species are persisted, enabled immediate channels are attempted, and email work is enqueued durably
    8. a separate worker delivers due email rows and records acceptance or retry state

    Important scheduling note:

    • the app now saves a per-user check_interval choice with values:
    • 5m
    • 1h
    • daily
    • weekly
    • monthly
    • never
    • the backend API and Postgres model persist that value
    • Beat is still driven by the shared cadence from BIRD_ALERTS_POLL_INTERVAL_SECONDS
    • the scheduler enforces each user's interval by selecting only due next_check_at values
    • never excludes the user from scheduled checks

    Scheduling Flow¶

    flowchart TD Beat["Celery Beat"] --> Schedule["schedule_all_clusters"] Schedule --> LoadUsers["Claim active users whose next_check_at is due"] LoadUsers --> Advance["Advance last_checked_at and next_check_at"] Advance --> Build["Build location clusters from due users"] Build --> Queue["Queue one check_cluster task per cluster"] Queue --> ClusterTask["check_cluster"] ClusterTask --> Fetch["Fetch cached / live eBird sightings"] Fetch --> Diff["Diff by user against user_seen_species"] Diff --> Persist["Insert new seen species"] Persist --> Immediate["Attempt enabled push / webhook"] Persist --> EmailQueue["Enqueue idempotent email work"] EmailQueue --> Deliver["Outbox worker delivers due rows"] Deliver --> Accepted["Store provider acceptance"] Deliver --> Retry["Classify failure and schedule retry"]

    6. Diff Engine¶

    The diff engine is the core of the alert-value logic.

    It compares:

    • the species currently present in a cluster
    • against each user's already-seen species set

    Only the newly seen species are:

    • inserted into user_seen_species
    • sent to the notification dispatcher

    This prevents noisy repeat notifications across poll cycles and restarts.

    7. Notification Dispatcher¶

    Source:

    • bird-agent/nearby_bird_alerts/notifications.py

    Supported channels:

    • push
    • email
    • webhook

    The dispatcher only sends on channels that are configured and enabled for a given user. Email is invoked by the durable outbox worker; push and webhook delivery remain in the immediate cluster-processing path.

    Notification Flow¶

    flowchart LR New["New species for user"] --> Push["Push notification"] New --> Webhook["Webhook POST"] New --> Outbox["Durable email outbox"] Outbox --> Email["Email provider"] Email --> Accepted["Accepted"] Email --> Retry["Retryable / permanent failure"]

    iOS Push Delivery Notes¶

    The iOS push path that was verified on 2026-06-06 is:

    1. the app registers an Expo push token on the physical iPhone
    2. the app saves that token to /birds/users/{external_id}
    3. the backend stores it in users.push_token
    4. the Celery worker detects new species for that user
    5. the notification dispatcher posts to Expo Push API
    6. Expo forwards to APNs using the EAS-managed push credentials for the app bundle id
    7. APNs delivers the notification to the iPhone

    Important operational notes:

    • a saved Expo push token in Postgres does not guarantee iOS delivery on its own
    • Expo/EAS must also have valid APNs credentials for:
    • com.anonymous.my-bird-app
    • if those APNs credentials are missing, Expo returns:
    • InvalidCredentials
    • Could not find APNs credentials ...

    Useful verification commands:

    Check that the app saved the push token:

    select external_id, email, push_token, check_interval, is_active
from users
where external_id = 'Ora8tDnihwWQ89L6RjlIk4uSL4H2';

    Send a direct Expo test push:

  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{
    "to":"ExponentPushToken[REPLACE_ME]",
    "title":"Bird spotted nearby!",
    "body":"Test notification from Bird Platform",

    Trigger a real nearby-bird poll:

    Watch the worker:

    The server now logs:

    • when a user has new nearby sightings
    • which notification channels are being used
    • the Expo ticket id returned for accepted push sends

    Key values include:

    • BIRD_ALERTS_DATABASE_URL_SYNC
    • BIRD_ALERTS_REDIS_URL
    • BIRD_ALERTS_EBIRD_API_KEY
    • BIRD_ALERTS_POLL_INTERVAL_SECONDS
    • notification channel settings
    • independent push and email preferences

    Source:

    • bird-agent/nearby_bird_alerts/config.py

    Migrations¶

    The alerts tables use a dedicated Alembic config:

    • bird-agent/alembic-nearby-bird-alerts.ini
    • bird-agent/alembic_nearby_bird_alerts/env.py

    This keeps the Postgres migration path separate from the legacy SQLite-backed application data.

    The migration history also owns:

    • notification_outbox, including unique deduplication, status, and retry-time indexes;
    • push_notifications_enabled and email_notifications_enabled user preferences.

    Current Boundary¶

    This module is integrated into the current backend, but it is intentionally isolated.

    Today:

    • core Bird Platform species and predictions still run through the main backend data model
    • nearby bird alerts run through their own Postgres-oriented module

    That boundary makes it easier to:

    • adopt Postgres gradually
    • move the broader backend toward Hetzner and a more production-native database layout
    • keep the alerting system scalable without rewriting the entire app in one step
